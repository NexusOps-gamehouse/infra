## 1. 빠른 시작

백엔드가 떠 있다는 전제로 세 단계다. 자세한 것은 2절.

```bash
cd infra

# 1. 시딩 — 계정 600 · 글 300 · 신청 1,000 + 토큰 사전 발급 (약 20초)
./load-test/seed/generate.sh

# 2. 정리 잡 — 별도 터미널에서 회차 내내 켜 둔다
./load-test/cleanup/steady-state.sh

# 3. 회차 실행
./load-test/run.sh smoke      # 1분. 경로 검증
./load-test/run.sh round-a    # 18분 30초. 판정 회차
```

> **2번을 빠뜨리면 회차가 통째로 오염된다.** 시나리오 5 가 초당 6건씩 글을 만드는데
> 목록 API 에 페이징도 상한도 없어서, 15분이면 300 → 5,700 건이 된다. 응답이 300KB →
> 5MB 로 불어나면 "135 RPS 에서의 성능" 이라는 말 자체가 성립하지 않는다.

## 2. 실행

> **로컬은 k6 네이티브 + 터미널 출력만 쓴다.** Prometheus·Grafana·대시보드를 띄우지 않는다.
> 로컬의 목적은 스크립트와 경로 검증이지 성능 판정이 아니라서, 숫자를 보관할 이유가 없다.
> 관측 스택을 안 띄우면 회차 중 Discord 알람도 울리지 않는다.

### 준비 (1회)

```bash
cd infra

# 대상만 띄운다. depends_on 이 postgres·rabbitmq 를 같이 올린다.
# frontend 와 관측 스택은 API 부하 테스트에 필요 없다.
docker compose --env-file .env.local \
  -f docker-compose.yml -f docker-compose.local.yml up -d backend

# 설계 가정 검증
./load-test/preflight/response-size.sh      # PostDto 실제 크기
./load-test/preflight/actuator-labels.sh    # 힙 id · GC 종류 실물
./load-test/preflight/histogram-buckets.sh  # SLO 값이 버킷 경계 위인가
```

### 회차 전 점검

```
□ backend 가 떠 있는가              curl localhost:8080/api/posts
□ 시딩이 1시간 이내인가             PENDING_TTL = 1시간
□ 정리 잡이 돌고 있는가             별도 터미널
□ scale 파일과 시딩이 같은가        assertSeed() 가 자동으로 잡는다
```

마지막 항목은 자동이다. 어긋나면 회차가 시작되기 전에 멈춘다.

```
[seed] 계약 ① 불일치 — seed/generate.sh 를 다시 돌릴 것
  - 프로파일 'smoke' ≠ 기대 'round' — 다른 규모로 시딩된 데이터다
  - 계정 5 ≠ 기대 600
```

### 회차 실행

**회차마다 세 가지를 순서대로 한다.**

```bash
# 1. 시딩 — 회차 사이마다 다시 돌려 상태를 동일하게 되돌린다.
#    안 하면 앞 회차가 남긴 데이터 위에서 재기 때문에 회차별 비교가 성립하지 않는다.
./load-test/seed/generate.sh

# 2. 정리 잡 — 별도 터미널에서 회차 내내 켜 둔다
./load-test/cleanup/steady-state.sh

# 3. 회차
./load-test/run.sh round-a
```

**2번은 회차 A·B·C 에 전부 필요하다.** 세 회차 다 시나리오 8개를 투입하고, 그중 시나리오 5
(`POST /api/posts`)가 계속 글을 만든다. 회차 D 만 시나리오 1 단독이라 필요 없다.

| 회차 | 시나리오 5 가 만드는 글 | 정리 잡 |
| --- | --- | --- |
| A | 6 RPS × 15분 ≈ 5,400 건 | **필수** |
| B | 배율 1/3~2 × 12분 ≈ 4,300 건 | **필수** |
| C | 4분 5초 (270 구간에서 12 RPS) | **필수** |
| D | 안 돈다 | 불필요 |

> 정리 잡을 안 켜면 **회차는 정상으로 끝나고 목록만 조용히 불어난다.** 에러가 안 나므로
> 결과를 볼 때까지 모른다. p95 가 올랐을 때 부하 탓인지 데이터 탓인지도 가릴 수 없다.

모든 회차는 `k6/rounds/` 아래 파일 하나가 진입점이다. 시나리오 8개는 `options.scenarios` 로
완전히 분리돼 있고 실행기는 `ramping-arrival-rate` 다 — **투입은 RPS 기준이고 VU 는 결과로 관찰한다.**
`ramping-vus` 를 쓰면 서버가 느려질수록 투입 RPS 가 저절로 줄어서
"135 RPS 에서의 p95" 가 아니라 "서버가 낼 수 있는 만큼에서의 p95" 를 재게 된다.

**`run.sh` 로 돌린다.** k6 를 직접 불러도 되지만, 래퍼가 회차 전후로 네 가지를 더 한다 —
시딩 프로파일 확인, `testid` 부여, exit code 기록, `manifest.json` 저장.

```bash
cd infra

# 스모크 — 경로 검증. 시나리오당 3초에 1회, 1분
SCALE=smoke ./load-test/seed/generate.sh
SCALE=smoke ./load-test/run.sh smoke

# 회차 A — 판정. 15분 + 앞뒤 3분30초
./load-test/seed/generate.sh          # SCALE 없이 = round 프로파일 (600·300·1,000)
./load-test/run.sh round-a

# 회차 B — Break Point 탐색 (12분)
./load-test/run.sh round-b

# 회차 C — 스파이크 (4분5초)
./load-test/run.sh round-c

# 회차 D — 데이터 증가. 게시글 수를 바꿔가며 4번 반복
./load-test/run.sh round-d                 # 300건
./load-test/seed/grow.sh 1000              # 채우고 meta.json 갱신
./load-test/run.sh round-d                 # 1,000건
./load-test/seed/grow.sh 3000
./load-test/run.sh round-d                 # 3,000건
./load-test/seed/grow.sh 10000
./load-test/run.sh round-d                 # 10,000건

# 원시 데이터까지 (회차 A 기준 압축 전 400MB 대)
./load-test/run.sh round-d --raw
```

**`SCALE` 은 시딩과 회차에 같은 값을 준다.** 한쪽만 주면 회차가 시작되기 전에 멈춘다.

```
시딩 프로파일이 다르다: 지금 데이터='smoke' / 이 회차가 기대='round'
  'round' 규모로 다시 시딩한다: ./load-test/seed/generate.sh
```

스모크 데이터(계정 5개)로 회차를 돌리면 여러 VU 가 같은 계정을 잡아 500 이 나고,
그건 서버 결함과 구분되지 않는다. 그래서 경고가 아니라 정지다.

`SCALE` 은 경로가 아니라 **프로파일 이름**이다 — `smoke` → `scale.smoke.json`.
경로로 받으면 bash 는 실행 위치(CWD) 기준으로, k6 의 `open()` 은 파일 위치 기준으로 풀어서
같은 문자열이 양쪽에서 다른 파일을 가리킨다. 이름으로 받으면 어디서 실행하든 같다.

<details>
<summary>k6 를 직접 부르는 경우</summary>

결과 파일과 `testid` 가 남지 않는다. 스크립트만 빠르게 확인할 때 쓴다.

```bash
SCALE=smoke k6 run load-test/k6/rounds/smoke.js
k6 run load-test/k6/rounds/round-a-load.js
```

</details>

### 회차가 남기는 것

```
results/20260812-181354-round-a/
  summary.txt      사람이 읽을 판정 요약        약 2 KB
  summary.json     k6 원본 구조. 재분석용       약 5 KB
  manifest.json    시딩 meta 사본 · exit code · 러너 정보   약 1 KB
```

`testid` 는 디렉토리 이름이자 k6 태그다. **둘이 같은 값이라 Grafana 에서 `$testid` 로 고른
그래프와 `results/` 의 폴더가 이어진다.**

**`--raw` 는 기본으로 끈다.** 이유는 용량이 아니다 — 압축하면 회차 A 가 25 MB 뿐이다.
압축 *전* 552 MB 를 회차 내내 실시간으로 만들어내면서 CPU 와 디스크 I/O 가 부하 생성과
경쟁하고, **러너가 먼저 포화되면 `dropped_iterations` 가 나서 그 구간이 폐기된다.**

| 회차 | `--raw` | 이유 |
| --- | --- | --- |
| A | **끈다** | 15분 지속이라 러너 부담이 가장 크다. 판정 회차라 오염을 감수할 수 없다 |
| B · C | 필요하면 | Break Point 순간의 요청 단위 데이터가 쓸모 있다. 켠 회차는 결과에 병기한다 |
| D | 켜도 무해 | 1 RPS × 3분 × 4구간 ≈ 720 요청 ≈ **3 MB** |

로컬에서는 `results/` 가 그냥 남는다. **AWS 회차는 러너를 종료하면 같이 사라지므로 회수 절차가
따로 필요하다**

### 끝낼 때

```bash
# 테스트 데이터 전량 삭제 + seed/data/ 정리
./load-test/seed/reset.sh
```

세 가지 정리 수단의 쓰임이 다르다.

| | 무엇을 지우나 | 언제 |
| --- | --- | --- |
| `generate.sh` | 전부 지우고 **곧바로 다시 시딩** (`00-reset` 이 1단계) | 회차 사이 |
| `cleanup/steady-state.sh` | 부하 계정이 만든 글만. `[SEED]` 는 안 건드린다 | 회차 **중** 상시 |
| `seed/reset.sh` | 전부 지우고 **비운 채로 둔다**. `seed/data/*.json` 도 함께 | 부하 테스트 종료 |

`reset.sh` 가 JSON 까지 지우는 이유: DB 만 비우고 `post-ids.json` 을 남기면 없는 PK 를 가리키게 되고,
그 상태로 회차를 돌리면 시나리오 2·4 가 전부 404 를 받는다. **404 는 이제 실패로 잡히므로 회차는
끝까지 정상으로 돌고 결과만 무의미해진다.**

## 3. 결과 읽는 순서

**순서가 중요하다.** 무효한 측정의 p95 를 해석하는 것은 시간 낭비가 아니라 **잘못된 결론의
출처**다. 판정보다 유효성을 먼저 본다.

### 0단계 · 이 측정이 유효한가

여기서 하나라도 걸리면 **아래 단계를 보지 않고 재측정한다.**

| 확인 | 어디서 | 걸리면 |
| --- | --- | --- |
| `dropped_iterations` = 0 | `summary.txt` 투입 | **구간 폐기.** 목표 rate 를 못 채운 것이라 서버가 느린 것과 구분되지 않는다 |
| 달성 RPS ≈ 목표 | `summary.txt` 투입 | 러너 CPU·네트워크를 먼저 본다. 러너 여유 + 서버 포화여야 원하는 관측이다 |
| 시딩 프로파일·건수 | `manifest.json` 의 `seed` | 폐기. `assertSeed()` 가 보통 시작 전에 잡는다 |
| 정리 잡이 돌았는가 | 별도 터미널 | 목록이 300 → 5,700 건으로 불어나 회차 내내 조건이 달라진다 |
| `exitCode` | `manifest.json` | **99 는 오류가 아니라 결과다** (threshold 위반, 회차는 완주). 그 외 값은 실행 오류라 결과를 쓰지 않는다 |

### 1단계 · 판정 (회차 A 에만 해당)

**세 조건을 전부 만족해야 합격이다.**

```
등급별 p95 충족   AND   5xx < 0.1%   AND   dropped_iterations = 0
```

- **등급별로 본다. 전체 합산 p95 는 쓰지 않는다** — 무거운 API 가 가벼운 API 에 희석돼
  "평균적으로는 괜찮다" 는 잘못된 답이 나온다
- **인증 등급은 가용성 판정에서 뺀다.** 1 RPS × 15분 = 900건이라 5xx 한 건이 0.11% 가 된다.
  지연(p95 < 1s)만 판정하고 5xx 는 절대 건수로 조사한다
- **최종 판정은 서버 측 비율형 지표로 한다.** `summary.txt` 는 k6 가 본 값이고, 판정은
  Grafana 의 `http_server_requests_*` 로 한다. k6 threshold 는 조기 신호용이다

### 2단계 · 불합격이면 어디가 먼저 무너졌나

**순서대로 좁힌다.** 이 회차의 목적은 합격 도장이 아니라 이 좌표다.

| 순서 | 관측 | 결론 |
| --- | --- | --- |
| 1 | **HikariCP `pending` > 0** | **풀 병목 확정.** 1순위 후보다 (기본값 10) |
| 2 | Tomcat `busy_threads` 가 200 근접 | 스레드 고갈. 여기서부터 응답시간이 선형이 아니라 급격히 나빠진다 |
| 3 | CPU 100% | N+1 · 직렬화 · 객체 생성 |
| 4 | **응답 지연 + CPU·메모리 여유** | 가장 위험한 신호. 스레드 부족이거나 DB Lock·트랜잭션 대기다 |

> **p95 가 주기적으로 튀면 GC 부터 본다.** 실측 결과 이 환경은 **Serial GC** 라
> major GC 가 stop-the-world 단일 스레드다 (6절 실측 참조).

### 3단계 · 합격이어도 반드시 볼 것 — 추세

**"통과했다" 와 "안정적이다" 는 다르다.** Sustained 15분 동안 아래가 **평평한지 우상향하는지**만 본다.

| 지표 | 우상향이면 |
| --- | --- |
| JVM 힙의 **GC 직후 저점** | 누수 신호. 고점만 오르고 저점이 평탄하면 일시적 대용량 할당(→ 페이징) |
| HikariCP `active` · Tomcat `busy` | 부하가 일정한데 늘면 커넥션·스레드가 반환되지 않는 것 |
| 등급별 p95 | 후반으로 갈수록 상승 = 지금은 통과지만 곧 무너진다 |

p95 상승은 누수가 아니라 **데이터 축적** 때문일 수도 있다. **정리 잡이 정상 동작했는지를
먼저 확인해** 원인을 가른다.

### 4단계 · 오해하기 쉬운 지표

| 지표 | 이렇게 읽으면 틀린다 | 실제 뜻 |
| --- | --- | --- |
| `lt_client_errors` = 0 | "4xx 가 없으니 완벽" | **시나리오 4 가 안 돈 것이다.** 중복 신청은 정상이고 회차 끝에 약 5% 까지 오른다 |
| `http_req_failed` | "5xx 만" | **5xx + 예상 밖 4xx + 연결 실패.** 시나리오마다 기대 상태코드가 다르다 |
| `lt_client_errors` = 0 | "4xx 가 없으니 완벽" | **시나리오 4 가 안 돈 것이다.** 중복 신청은 정상이고 회차 끝에 약 5% 까지 오른다 |
| VU 300 | "부하를 크게 줬다" | **투입값이 아니라 결과다.** 응답이 가정(사고시간 5초)보다 느리다는 뜻 |
| 전체 `http_req_duration` p95 | 판정 근거 | 희석된 값. 판정에 쓰지 않는다 |
| 등급 행이 `집계 안 함` | "요청이 없었다" | **k6 는 threshold 가 참조하는 서브메트릭만 만든다.** 스모크는 등급 threshold 가 없어서 그렇다 |

### 회차별로 보는 것이 다르다

| 회차 | 무엇을 본다 |
| --- | --- |
| **A** | 위 1~3단계 전부. **유일한 판정 근거** |
| **B** | Break Point 좌표(몇 RPS 에서 무엇이 먼저) + 45 RPS 로 낮춘 뒤 **2분 내 복구되는지** |
| **C** | 풀·스레드 고갈 여부. **270 RPS 는 회차 B 최상단과 같은 값이라**, 점진(B) 과 순간(C) 의 차이가 곧 큐잉의 영향 |
| **D** | 건수별 p95 곡선이 500ms 를 뚫는 지점(→ 페이징 시점) + 힙 **저점** 패턴(평탄=페이징 / 계단식 상승=누수) + OOM 발생 건수 |

## 4. 부하 설계 — 왜 이 숫자인가

### 시나리오와 회차 — 숫자와 알파벳

문서와 코드에 숫자와 알파벳이 같이 나온다. **층위가 다르다.**

| | 무엇 | 어디에 대응 |
| --- | --- | --- |
| **시나리오 1~8** | **무엇을 때리는가.** 엔드포인트 하나가 시나리오 하나 | `k6/scenarios/s1~s8` · `options.scenarios` 의 키 `S1`~`S8` |
| **회차 A~D** | **어떻게 때리는가.** 부하를 어떤 모양으로 투입하는 유형 | `k6/rounds/round-a~d` |

**회차 하나 = 시나리오 1~8 전부를 같은 배율로 동시에 투입하는 것**이다 (회차 D 만 시나리오 1 단독).
숫자는 대상, 알파벳은 방식이다.

회차는 **서로 다른 날 돌린다.** t3 CPU 크레딧이 회복되어야 하므로 하루에 몰아서 돌리면
뒤 회차가 baseline 성능으로 제한된 상태에서 측정된다.

### 사용자 행동을 어떻게 숫자로 옮겼나

부하량을 감으로 잡지 않았다. **동시 접속자 수 하나**에서 두 갈래로 계산했다.

```
가정: 동시 접속 150명 · 사고시간(think time) 5초 · 여정 1회 = 평균 4 요청

① 여정 부하   150명 ÷ 5초 = 초당 30여정 × 4요청 = 120 RPS
② 폴링 부하   150명 ÷ 10초 주기                 =  15 RPS
                                          합계 = 135 RPS
```

**폴링을 따로 뺀 것이 핵심이다.** 알림 폴링은 사용자가 클릭해서 생기는 게 아니라 **시계가**
돌린다. 사용자 행동 비중표에 섞으면 부하를 잘못 잡는다. 접속자 수에만 비례하므로 별도 축으로
두고, **모든 단계에서 여정 : 폴링 = 8 : 1** 을 유지한다.

> **투입은 RPS 로 하고 VU 는 결과로 관찰한다.** "동시 150명"은 부하 크기가 아니다.
> 135 RPS 를 넣었는데 VU 가 150 근처면 위 가정이 일관된 것이고, 300 을 넘으면
> **응답이 가정보다 느리다**는 뜻이다. VU 는 투입값이 아니라 계기판이다.

### 여정 모델 — 4 요청의 구성

위 계산의 "4 요청"을 엔드포인트 단위로 펼친 것이다. **이 모델이 비중표의 근거이고, 비중표가
목표 RPS 를 만든다.**

```
        [ 로그인 완료 ]
              │
              ▼
  [ 1. 내 정보  /users/me ]        여정 몫 15%
              │
              ▼
  [ 2. 목록    /posts ]            여정 몫 45%
              │
              ▼
  [ 3. 상세    /posts/{id} ]       여정 몫 25%
              │
       ┌──────┴──────┐
  [ 40% 이탈 ]  [ 60% 행동 ]
                     │
        ┌────────────┼────────────┐
   (53%)│       (33%)│       (13%)│
        ▼            ▼            ▼
  [ 4a. 참가신청 ] [ 4b. 글 작성 ] [ 4c. 신청 현황 ]
      몫 8%          몫 5%          몫 2%
```

**여정 몫은 "도달 확률"이 아니라 "요청 건수 비율"이다.** 여정 몫 × 4 = 여정당 평균 호출 횟수.

| 단계 | 여정 몫 | × 4 = 여정당 호출 | 해석 |
| --- | --- | --- | --- |
| 1. 내 정보 | 15% | 0.6회 | 매 여정마다 부르지는 않는다 (재방문 시 생략) |
| 2. 목록 | 45% | **1.8회** | 상세를 보고 목록으로 되돌아오는 **왕복**이 있다 |
| 3. 상세 | 25% | **1.0회** | 여정당 정확히 1회 |
| 4. 분기 | 15% | 0.6회 | **여정의 60% 만 행동으로 이어진다** |
| **합계** | **100%** | **4.0회** | 위 계산의 입력값과 일치 |

**이 환산을 안 하면 모델이 모순돼 보인다.** "순차 흐름인데 왜 단계마다 비중이 다른가"의 답이
**왕복과 생략**이다 — 목록은 1회를 넘고, 내 정보는 1회에 못 미친다.

### 비중 → 목표 RPS

| # | 요청 | 비중 | Peak RPS | 등급 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 1 | `GET /api/posts` | 45% | **54** | `list_read` | 페이징 없음. 송신량을 지배한다 |
| 2 | `GET /api/posts/{id}` | 25% | 30 | `list_read` | |
| 3 | `GET /api/users/me` | 15% | 18 | `light_read` | |
| 4 | `POST /api/posts/{id}/apply` | 8% | 10 | `write` | 중복 신청 400 이 정상 |
| 5 | `POST /api/posts` | 5% | 6 | `write` | 데이터가 쌓인다 → `cleanup/` |
| 6 | `GET /api/my/applications` | 2% | 2 | `light_read` | |
| | **여정 소계** | | **120** | | |
| 7 | `GET /api/notifications` | 시계 기반 | **15** | `light_read` | 폴링. 여정 밖 |
| | **합계 (판정 부하)** | | **135** | | |
| 8 | `POST /api/auth/login` | 여정 외 | 1 | `auth` | **135 에 미포함** |

읽기 : 쓰기 = 119 : 16 ≈ **88 : 12**

**시나리오 8 을 여정 밖에 둔 이유.** 여정 모델은 *이미 로그인한* 사용자의 행동이고, 로그인은
여정 진입 **전에 1회** 발생한다. 150명이 평균 5분 체류한다고 보면 신규 유입은
`150 ÷ 300초 = 0.5 RPS`, 올림해서 1 RPS 다. 총 부하의 0.7% 라 판정선에 영향이 없다.

빼지는 않는다 — 빼면 인증 등급 목표를 판정할 데이터가 안 나온다. 다만 **BCrypt 는 CPU 집약적**
이라 이 소량이 CPU 그래프에 미치는 영향은 따로 본다.

### ⚠️ 여정 순서대로 부르지 않는다

여정 모델은 **순서를 재현하는 것이 아니라 비율을 재현한다.** 시나리오 8개는 각자 독립된
arrival-rate 로 **동시에** 투입된다. "내 정보 → 목록 → 상세 → 분기" 를 한 VU 가 이어서 밟지 않는다.

**왜 그렇게 했나.** k6 arrival-rate 의 `rate` 는 **iteration 단위**다. 여정 전체를 1 iteration 으로
묶으면 `rate: 30` 이 30 여정 = **120 RPS** 가 되어 의도의 4배가 나간다. 엔드포인트별로 쪼개
**1 iteration = 1 요청**으로 만들면 `rate` 가 곧 RPS 가 되고, 위 비중표를 그대로 옮길 수 있다.
비중을 정확히 통제하는 방법은 이것뿐이다.

**무엇을 얻고 무엇을 포기했나.**

| | |
| --- | --- |
| 얻은 것 | 시간당 요청 **비율**의 정확한 통제. 서버가 받는 부하 구성은 동일하다 |
| 포기한 것 | 세션 내 **순서 의존**. "목록에서 본 글을 상세 조회" 같은 연결이 없다 |

포기해도 되는 이유는 이 API 들이 **서로의 상태에 의존하지 않기** 때문이다. 다만 그 대가로
시나리오 2·4 는 대상 글을 **시딩 300건 풀에서 무작위로** 고른다 (`seedPostId()`).
목록 응답에서 ID 를 이어받지 않는다.

### 회차별 부하 프로필

배율은 **모든 시나리오에 동일하게** 곱한다. 그래야 비중표와 8:1 이 전 구간에서 유지된다.

| 배율 | 총 RPS | 여정 | 폴링 | 상당 동시 접속자 |
| --- | --- | --- | --- | --- |
| `OFF_PEAK` 1/3 | 45 | 40 | 5 | 50명 |
| `MID` 2/3 | 90 | 80 | 10 | 100명 |
| **`PEAK` 1** | **135** | **120** | **15** | **150명** |
| `S133` 4/3 | 180 | 160 | 20 | 200명 |
| `S167` 5/3 | 225 | 200 | 25 | 250명 |
| `S200` 2 | 270 | 240 | 30 | 300명 |

> **스트레스 단계에서 폴링도 같이 올리는 이유.** 재현하려는 상황은 "같은 사용자가 더 빨리
> 클릭하는 것"이 아니라 **"접속자가 더 많아진 것"**이다. 접속자가 늘면 폴링도 같은 비율로 는다.

**회차 A — Load.** 유일한 판정 근거.

```
 RPS
 135 ┤          ╭────────────────────────╮
     │         ╱   Sustained 15분 ← 판정   ╲
  45 ┤   ╭────╯                             ╲
   0 ┼───╯                                   ╲──►
     └─30s─┴──2m30s──┴────── 15m ──────┴─30s─┘
      Warm-up  Ramp-up    Sustained     Cool-down
```

Warm-up 은 JIT 컴파일·커넥션 풀 초기화용이라 집계에서 뺀다. **Sustained 15분은 줄이지 않는다** —
5xx 0.1% 기준 자체가 `135 RPS × 15분 = 121,500 요청`(허용 121건)에서 나왔고, 구간을 줄이면
분모가 달라진다. GC 누적·커넥션 누수도 짧은 구간에서는 안 보인다.

**회차 B — Stress.** Break Point 탐색. 2분마다 45 RPS 씩 계단.

```
 270 ┤                        ┌────┐
 225 ┤                  ┌─────┘
 180 ┤            ┌─────┘
 135 ┤      ┌─────┘
  90 ┤ ┌────┘
  45 ┤─┘
     └─2m──2m──2m──2m──2m──2m─►
```

**5xx 5% 초과에서 중단한다** (`abortOnFail`). 이건 합격선이 아니라 **탐색용 중단선**이다 —
합격선은 0.1% 이고, 회차 B 는 애초에 판정 대상이 아니라 한계 좌표를 찾는 회차다.

**회차 C — Spike.** 순간 폭증.

```
 270 ┤        ╭──────────╮
  45 ┤────────╯          ╰──────────────
     └─45s──┴10s┴──1m──┴10s┴─── 2m ───►
                            회복 관측
```

**270 은 회차 B 최상단과 같은 값이다.** 같은 부하를 *점진적으로* 올렸을 때(B)와 *순간적으로*
던졌을 때(C)의 차이가 곧 큐잉·커넥션 풀 고갈의 영향이라, 같은 좌표에서 비교하려고 맞췄다.
중단시키지 않고 끝까지 돌려 **회복 구간**을 본다.

**회차 D — Data Growth.** 시나리오 1 단독, `constant-arrival-rate` 1 RPS × 3분.

부하가 아니라 **게시글 건수**가 변수다. 300 → 1,000 → 3,000 → 10,000 건으로 늘리며 반복한다.

```
 RPS │ 1 ── 1 ── 1 ── 1     ← 내내 고정
 건수│ 300  1k   3k   10k   ← 이것만 바뀐다
     └ 3m ┴ 3m ┴ 3m ┴ 3m
        ↕    ↕    ↕
      재시딩 (측정 구간 아님)
```

**왜 1 RPS 인가.** 건수가 늘면 응답 본문이 수 MB 가 된다. 54 RPS 로 재면 서버가 아니라
**네트워크 대역폭이 먼저 천장에 닿아** 측정이 무효가 된다. 10,000건을 54 RPS 로 내보내면
초당 수백 MB 다. 여기서 SLO 를 판정하지 않는다 — **데이터가 커지면 깨지는 것이 당연하고,
'언제 깨지는가'가 답이다.**

| --- | --- | --- |
| `scale.json` | 규모의 단일 출처. `config.js`(k6)와 `generate.sh`(jq)가 **같은 파일**을 읽는다 | 한쪽만 고쳐서 A 는 600 을 가정하고 B 는 300 을 시딩한다 |
| `db.sh` | `LT_DB_*` 만 보고, 로컬이 아니면 호스트명 재입력을 요구한다 | `.env` 의 `DB_HOST` 는 **공용 dev RDS** 다. `00-reset` 이 그것을 비운다 |
| `_post-rows.sql` | 게시글 INSERT 를 한 곳에 모은다 | 시딩과 회차 D 증분이 갈라진다 (실제로 한 번 갈라졌다) |
| `generate.sh` | `INSERT` 후 PK 를 되받아 JSON 으로 떨군다. 토큰 600개 사전 발급 | SQL 파일은 자기 실행 결과를 파일로 못 내보낸다. `setup()` 로그인은 순차라 90초+ |
| `data.example/` | 스택 없이 A 가 로더·태그·매핑을 검증한다 | A 가 B 의 postgres 를 기다린다. 1단계가 직렬이 된다 |
| `cleanup/` | 회차 중 데이터 크기를 고정한다 | 목록이 300 → 5,700 건. p95 상승이 부하 탓인지 데이터 탓인지 못 가린다 |
| `preflight/` | 부하 규모를 산정할 때 세운 가정을 실측으로 검증한다 | PostDto 600B 로 잡았던 것이 실제 1,014B 인 것을 회차 끝나고 안다 |

### 접두사 규칙

```
[SEED] …   generate.sh 가 시딩한 고정 글. 시나리오 2·4 의 대상 풀
```

`posts` 테이블에 "테스트용" 플래그 컬럼이 없어서 `title` 로 표시한다. 테스트를 위해 운영 스키마를
바꾸는 것보다 낫다.

**다만 삭제 판정은 제목이 아니라 작성자로 한다.**

```
[SEED] 글 → seedauthor@test.local   ← cleanup 이 절대 안 건드린다
런타임 글 → lt0001~lt0600           ← cleanup 이 지운다
```

시나리오 5 가 붙이는 제목 접두사에 의존하면, A 가 접두사를 빠뜨리는 순간 아무것도 안 지워진다.
그런데 **회차는 정상으로 끝나고 목록만 조용히 불어난다.** 작성자로 고르면 제목과 무관하게 동작한다.

## 6. 실측으로 확인된 것

부하 규모를 산정할 때 세웠던 가정과 실제가 다른 부분이다. `preflight/` 로 직접 쟀다.
**회차 결과를 해석할 때 이 값들이 전제가 된다.**

| 항목 | 문서 가정 | 실측 | 왜 중요한가 |
| --- | --- | --- | --- |
| PostDto 크기 | 600 B | **약 1,014 B** | 15분 회차 송신량 약 13 GB. 회차 D 의 10,000건 구간은 목록 응답 하나가 약 10 MB |
| GC | (미지정) | **Serial GC** | major GC 가 stop-the-world 단일 스레드다. p95 가 주기적으로 튀면 여기부터 본다 |
| 힙 | — | **200 MB** (컨테이너 700 MB) | 컨테이너 메모리가 1,792 MB 미만이라 JVM 이 Serial 을 고른다. 회차 D 의 OOM 이 예상보다 빠르다 |
| 힙 영역 이름 | — | `Eden Space` `Survivor Space` `Tenured Gen` | **G1 이 아니다** |
| 히스토그램 버킷 | 7개로 축소 | **uri 당 90개** | `slo:` 설정은 경계를 *추가*할 뿐 줄이지 않는다. SLO 값(200ms/500ms/1s)은 전부 경계 위라 보간 없이 읽힌다 |
| 응답 압축 | — | **없음** | 송신량이 그대로 대역폭이다 |
| `uri` 라벨 | — | `/api/posts/{id}` 로 묶임 ✅ | 서버측은 정상. k6 는 `SYSTEM_TAGS` 로 `url` 을 뺐다 |

다시 재려면 `preflight/` 3종을 돌린다. **로컬 수치는 성능 판정에 쓰지 않는다** — `platform: linux/amd64`
에뮬레이션이라 절대값이 무의미하다. 위 표는 절대값이 아니라 '환경의 성질'이라 유효하다.

## 7. AWS 회차로 옮길 때

**아래는 전부 아직 해당 없다.** 이 문서의 1~6절은 로컬 기준이고, 로컬의 목적은
"AWS 회차에 나갈 준비가 끝났다"를 증명하는 것이다. 여기 모아둔 것은 그때 달라지는 부분이다.

| | 로컬 (지금) | AWS 회차 |
| --- | --- | --- |
| **대상** | `localhost:8080` | 동일 VPC **사설 IP 직결** (`BASE_URL`) |
| **러너** | 이 맥 | 임시 EC2. **회차 동안만 띄우고 결과 회수 후 종료** |
| **DB** | `docker-compose.local.yml` 의 postgres | 운영 **스냅샷에서 복원한 임시 RDS** |
| **`preAllocatedVUs`** | 5 (`VUS.smoke`) | 회차 A 300 / B·C 600 — **여기서 처음 검증된다** |
| **`ulimit -n`** | 무관 | 사전 확대. 부족하면 `dropped_iterations` 가 난다 |
| **CPU 크레딧** | 무관 | 회차 전 `CPUCreditBalance` 확인. **고갈 이후 구간은 판정 제외** |
| **관측** | 안 띄운다 | **방식 미정** — 아래 참조 |
| **결과 수치** | 판정에 쓰지 않는다 | **여기서 처음 유효하다** |

### 관측을 어디에 둘지는 아직 정하지 않았다

k6 지표를 Prometheus 로 보내려면 수신 쪽에 `--web.enable-remote-write-receiver` 가 켜져 있어야
한다. 문제는 **운영 Prometheus 가 대상 EC2 에 함께 얹혀 있다**는 것이다.

| | 방식 | 운영 영향 |
| --- | --- | --- |
| 1 | 회차 동안만 운영 Prometheus 에 플래그를 얹고 원복 | k6 데이터가 같은 TSDB 에 섞여 **retention 2GB 를 나눠 쓴다.** 카디널리티가 튀면 운영 지표가 먼저 밀려난다 |
| **2** | **러너 EC2 에 부하 테스트 전용 Prometheus** | **없음.** 회차 끝나면 러너와 함께 사라진다 |
| 3 | k6 는 `results/` 파일만, 서버 지표는 운영 Prometheus 그대로 | 없음. 대신 k6 지표와 서버 지표를 같은 시간축에서 못 겹친다 |

**2번이 유력하다.** 운영 무영향인 데다, 회차 B·C 에서 **대상이 무너질 때 관측도 같이 죽는**
문제까지 풀린다 — 무너지는 순간의 지표가 곧 그 회차의 목적이다.

고르는 근거는 **로컬에서 실측한 카디널리티 증가폭**이다. 회차 1회 후
`prometheus_tsdb_head_series` 가 얼마나 늘었는지를 보고 정한다. 숫자 없이 지금 고르지 않는다.

### 결과 회수 — 러너를 끄기 전에

`run.sh` 가 남긴 `results/` 는 러너 EC2 의 디스크에 있다. **인스턴스를 종료하면 같이 사라진다.**
켜둔 채 잊는 것이 요금이 새는 가장 흔한 경로라 회차 직후 끄게 되는데, 그 전에 가져와야 한다.

```bash
scp -r ubuntu@<runner>:~/load-test/results/<testid> ./load-test/results/
```

`--raw` 를 켠 회차는 압축 상태로 25 MB 대다. 회수 시간을 감안한다.

### 회차 사이

- **회차 B·C 를 회차 A 와 같은 날 돌리지 않는다.** t3 CPU 크레딧이 회복되어야 한다.
- 회차마다 **시딩 상태를 동일하게 복원한다** (`generate.sh` 가 `00-reset` 부터 돈다).
  안 하면 회차별 비교가 성립하지 않는다.
- 러너를 **대상과 같은 AZ** 에 둔다. AZ 간 전송 요금이 없어지고, 사설 IP 직결이면
  Data Transfer Out 과금도 0 이다.
